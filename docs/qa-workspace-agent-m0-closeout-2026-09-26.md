## 2. 测量支持的决定

继续沿用 2 活动 / 8 排队，12 次主模型调用 / 24 次工具调用，14,000 单读 / 96,000 单运行返回字符，最多 8 文档。新资源共享预算；2,000 条限制用于应用层兜底扫描，数据库精确 COUNT 不因匹配数超过 2,000 截断。

同 fixture、Node、资源限额和 mock 模型下，三轮中位 p95 超过 `基线 × 1.5 + 5ms` 或 RSS 超过 `基线 × 1.25 + 32MiB` 必须调查。普通问答仍 1 次主调用、0 工具；热读后端 0 次；取消后无误提交、排队取消不调模型、许可全部释放。供应商延迟和数据库时间分别测量，不与这些合成毫秒数混算。

数据库结果支持稳定 ID 的 keyset 设计与按需 SQL 聚合；GIN 只在实际匹配的 FTS 查询计划中成立，当前 ILIKE 子串不因此自动加速。双语人工词表可命中固定 4/4 目标，单语词只覆盖同语 2/2；没有宣称一般跨语言检索质量。

标题 p95 约 1.03 秒，实际最多 211 输入 / 8 输出 token；两次英文问题返回中文，保留失败输出并明确降级。规则检查不能代替语义质量；M2 必须修正语言和表达质量后再做产品验收。未知 usage 不当零费用、未知完成状态不重试，以免测量脚本或后续任务重复计费。

新查询缓存的 2 MiB/用户、16 MiB/进程、60 秒是保守设计上限和容量核算；通用缓存尚未实现。新附件/草稿/客户端工具的限额是待接入协议，不能从已有原文路径推断它们已通过集成性能验收。
